## Payments, split settlement, holds, refunds, payouts (India + USA)

**Summary (from research):** VERIFIED PAYMENT ARCHITECTURE FOR THE POOL PROTOTYPE (checked 2026-09-29) INDIA (INR, UPI, cards, EMI): use Razorpay in test mode. - Test mode opens right after signup. No KYC is needed. - Flow: Orders API with transfers[] to the dealer's Route Linked Account, created with on_hold=true. - When the buyer confirms the delivery or pickup code, call PATCH /v1/transfers/:id with on_hold=false to release the dealer payout. POOL's commission is whatever it does not transfer. - Wave Drop rebate: pay it at pool close as a partial refund (POST refund with an amount, speed=optimum), plus reverse_all or a transfer reversal. - Suggested design (not a vendor feature): split each order into two transfers, (a) the base payout, released on the delivery code, and (b) a "rebate reserve" transfer kept on hold until pool close. Then the Wave Drop refund never has to claw money back from a dealer. HARD REGULATORY GATE (RBI PA Master Direction, 15 Sep 2025, read from the PDF text): - Para 10: a PA may not run a marketplace business. - Para 13(f): a marketplace may accept payments only for sellers onboarded on its platform. - Escrow permitted-debit (iv): paying a third party (the dealer) on the merchant's instruction is allowed only if the merchant (POOL) has annual turnover above Rs 40 lakh (or export turnover above Rs 5 lakh), and the payee deals directly with the payer. - Para 18(b): the escrow account cannot be used for Cash-on-Delivery. Pickup-code mutton pools must be prepaid through the PA. - Settlement timelines follow the PA–merchant agreement. Refunds route back through escrow. - Razorpay has applied this rule to Route. Live Route needs GST-3B proof of more than Rs 40L turnover plus approval of a use-case description (routepriority@razorpay.com, 5–7 business days). Pre-existing Route users who missed the 31 Dec 2025 deadline lost Route access. - The rule comes from RBI, so every Indian PA's split product (Cashfree, PayU, Pine Labs, Juspay) is bound by it. - Action: check whether the founder's existing Pvt Ltd has GST-3B turnover above Rs 40L and could be the merchant of record. Otherwise the investor demo runs fully in test mode, which is still real APIs, webhooks, holds and refunds, and the live pilot waits on eligibility. - Also: do not build seller payouts from POOL's own bank account (for example via RazorpayX). That would look like unauthorised payment aggregation. USA (USD): use Stripe Connect in a sandbox. - Why not Stripe India: it has been invite-only since May 2024, and India platforms cannot use separate charges and transfers. Live US operation needs a US entity (for example via Stripe Atlas, $500). - Flow:   1. Create a PaymentIntent with transfer_group=pool_id. If the pool closes within about 5–7 days, use capture_method=manual so joining places a real card hold.   2. When the buyer accepts, capture with amount_to_capture set to the accepted price. A partial capture releases the rest automatically.   3. If the buyer walks away, cancel the PaymentIntent.   4. On the delivery code, create a Transfer with source_transaction to the dealer's connected account, minus commission.   5. At pool close, pay Wave Drop as a partial refund. - Manual payouts can also hold a US connected account's balance for up to 2 years. - Onboard dealers with the embedded onboarding component. Stripe runs KYC. - Stripe says plainly that it does not provide escrow. Market this as "held until delivery", not "escrow". The same applies in India, where "escrow" is RBI's term for the PA's own account. TAX: - India: GST TCS of 0.5% under s.52 and TDS of 0.1% under s.194-O on dealer payouts (secondary sources only). - US: marketplace-facilitator sales tax via Stripe Tax. - US: the 1099-K threshold is back to more than $20k and more than 200 transactions (IRS, OBBB). LEDGER: keep a double-entry ledger in PostgreSQL from day one, with booking, hold, capture, transfer, rebate and refund entries. TigerBeetle, Formance and Blnk are options for later. AGENTIC RAILS (ACP, AP2, UCP, Visa Intelligent Commerce, Mastercard Agent Pay, Razorpay/NPCI agentic UPI) are real and active in 2026. They are all beta, pilot, waitlist or region-limited: Stripe's Agentic Commerce Suite covers the US, Canada and Europe only, not India. Show them in the pitch as roadmap, not as the prototype's payment path. For the prototype you can use right away: the Razorpay MCP server and the Stripe MCP / agent toolkit as developer tools.

## Open-source code and core platform tech (GitHub)

**Summary (from research):** PLATFORM-OSS LENS: what we build on and what we build ourselves. All repo facts below were checked live against the GitHub API (gh api) on 2026-09-29: licence file, stars, last push and latest release. Docs facts were checked on the official sites. 1) CORE FINDING: there is no production-grade open-source "pool + sealed bid + guaranteed price" engine to reuse. A GitHub search for "reverse auction", "sealed bid auction" and "group buying" returns only guides, toy apps, blockchain contracts and one 18-star Rust OTC RFQ engine. So the POOL engine is our own IP: pools, the booking deposit, sealed bids, accept/walk-away, Wave Drop slabs and handover codes. We build it as custom modules on a proven TypeScript commerce/marketplace core. ERPNext's request_for_quotation and supplier_quotation doctypes are domain reference only. 2) RECOMMENDED CORE: - Medusa v2 (v2.21.2, 28 Sep 2026, MIT) plus Mercur (v2.3.5, MIT). Mercur is a multi-vendor layer on Medusa 2.21. It gives us:   - seller onboarding   - an Offer module, where many sellers list offers against one master product (the closest primitive to dealer bids)   - rule-based commissions   - per-seller order splitting   - a pluggable IPayoutProvider (Stripe Connect is built in)   - admin and vendor panels, and a Next.js storefront - Critical constraint: Mercur's payout module talks to exactly ONE provider per deployment. That fits a two-region design: an India stack (Razorpay-Route-type custom payout provider + custom Medusa payment provider, INR) and a US stack (Stripe, USD), running the same codebase. The India stack's payment data then stays in India, as RBI requires. - Do NOT enable Medusa RBAC or SSO. Those files are under a proprietary ENTERPRISE-LICENSE, and switching the flag on counts as claiming you hold a commercial licence. - Medusa scheduled jobs are cron-only, so they cannot run per-pool timers. - Medusa ships only a Stripe payment provider. There is a community Razorpay plugin, but it has 17 stars and we found no evidence it supports split payments. 3) TIMERS: Temporal Cloud (MIT SDK) for pool close, bid window, accept window, holding payout until the delivery code is entered, and Wave Drop partial refunds at close. - Regions include AWS Mumbai (ap-south-1), Hyderabad (ap-south-2) and US. - Timers survive restarts; sleep() and condition() can wait for months. - Pricing: $50 per million actions, plus $150 of credits for 90 days. - Trigger.dev (Apache-2.0) is the lighter alternative. Inngest's server is under SSPL. 4) DATA: - PostgreSQL 18.6 (19 is only at Beta 4), plus PostGIS for dealer radius and pgvector for matching products (AI suggests, never invents). - Valkey 9 (BSD) instead of Redis 8, which is now tri-licensed RSAL/SSPL/AGPL. - BullMQ for jobs, Meilisearch for search. - Drizzle for services outside Medusa. **Summary (from research):** Checked 2026-09-30 against official docs, pricing pages and GitHub (via gh API). Recommended prototype stack. ## Product identification, price sources and link extraction

**Summary (from research):** Checked 2026-09-30 using official docs, GitHub (gh API), npm and live robots.txt/page tests. The main findings: (1) AMAZON. PA-API 5 is gone: the old docs URL now redirects to a Creators API deprecation notice, and PA-API calls return 403. Creators API needs 10 qualifying sales in the last 30 days. Its policy says content may only be used on a site whose principal purpose is advertising Amazon, and may not be used to promote products sold on any non-Amazon site. POOL shows dealer bids, so it cannot use Amazon catalog or price data. Recommendation: avoid. (2) FLIPKART. The Terms of Use (verified) ban any 'deep-link', 'page-scrape', 'robot', 'spider' or similar manual process. So POOL must not fetch Flipkart pages; the same applies to Amazon, though Amazon's own ToS page returned 503 and could not be read. Pattern for these two: parse the pasted URL only (ASIN from /dp/, Flipkart pid and slug), pull the model number from the slug, and have the buyer confirm. The Flipkart Affiliate API exists (product feed, keyword search, productId lookup), but whether new signups are open is unclear. (3) TESTED INDIAN RETAILERS. Reliance Digital and Vijay Sales robots.txt allow product pages. One product page from each, fetched server-side, carried schema.org Product JSON-LD with name, brand, INR price and availability, but NO GTIN/MPN (Vijay Sales has empty gtin/mpn fields). The model code sits inside the product name (for example GV-B23FFLMB and KGN56LB42I). Croma's Akamai edge refused even robots.txt to a plain request. - Consequence: for Indian appliances, identity has to rest on normalised model numbers, not GTIN. - Lowest-risk extraction pattern:   - fetch one page, only when the user asks   - honour robots.txt and ToU, and use no proxies or CAPTCHA bypass   - parse JSON-LD/OpenGraph (cheerio + metascraper; Crawlee/Playwright only when rendering is needed)   - Diffbot or Firecrawl cloud as fallback for brand sites   - never crawl, and cache briefly with source and timestamp (4) IDENTITY. Deterministic model-number normalisation plus a GTIN check digit when present. Then pgvector embedding recall over an ops-curated canonical catalogue (Open Icecat for enrichment), and an LLM verifier that must quote source fields and may answer 'unknown', followed by buyer confirmation. The open-source entity-matching libraries (Ditto, py_entitymatching) are stale since 2024, and Zingg is AGPL, so they are not needed for the prototype. (5) PRICE OPTIONS. - India: the pasted page's own price, plus SerpApi Google Shopping at demo scale. Google's DMCA claims against SerpApi were dismissed in July 2026 (with limited leave to amend). SerpApi's paid tiers include a $2M 'U.S. Legal Shield'. - USA: the Best Buy API (free key) for buyer-facing reference only. Its terms forbid use for the benefit of other retailers analysing Best Buy pricing, cap caching at 72 hours, and commerce apps must list Best Buy among checkout options. - Affiliate feeds for later: Admitad (Croma and Tata CLiQ programmes), and Impact for Walmart and Target. - Google Custom Search JSON API is closed to new customers and ends 2027-01-01. The Content API for Shopping sunset on 2026-08-18; the Merchant API that replaces it is seller-side only. - Keepa supports amazon.in (domain 10), but it is Amazon-derived data; use later, after checking its terms. (6) BANK/CARD OFFERS. No legitimate feed of offers running on third-party retailers was found. POOL can only run offers on its own checkout: Razorpay Offers in test mode now; Pine Labs Offer Discovery API (brand EMI with product_details, issuer offers) for production India; Juspay Offer Engine for enterprise. (7) LAW. - India: IT Act s.43(b) gives civil compensation for downloading, copying or extracting data without the owner's permission; s.66 makes it criminal when done dishonestly or fraudulently. Courts have not settled whether ToU bans are enforceable, so treat ToU bans as binding. - US: Van Buren (2021) narrowed CFAA. In hiQ v LinkedIn, hiQ won the CFAA point but lost on breach of contract, paying $500k and accepting an injunction (2022). Meta v Bright Data (2024): logged-off scraping was not a breach of Meta's terms. X v Bright Data was dismissed (2024). Amazon v Perplexity (9th Cir, 4 Aug 2026) vacated Amazon's CFAA injunction because the user, not Perplexity, accessed the site; contract and ToS claims remain open, and routing through the user's device mattered. - Licences: Firecrawl core is AGPL-3.0 (its SDKs are MIT). Use the cloud version or keep a self-hosted copy unmodified. Everything else recommended is MIT, Apache or BSD (pgvector uses the PostgreSQL licence).

## AI models, agent stack and advanced features

**Summary (from research):** What we should do, all checked on 2026-09-30 against official sites, npm, GitHub and Hugging Face: (1) Telugu and Hindi WhatsApp voice notes: use Sarvam saaras speech-to-text through its plain REST API. - Cost is ₹30 per hour of audio. A 30-second note costs ₹0.25, and 1,000 such notes cost ₹250. - Telugu (te-IN) is supported, OGG/Opus audio is accepted as-is, and there is a code-mixed mode. Real-time calls take up to 30 seconds of audio; the Batch API takes up to 1 hour. - Claude then turns the transcript into structured JSON, and we read it back to the buyer for confirmation. - Do not use the sarvamai npm SDK: it declares no licence and its GitHub repo returns 404. - Keep IndicConformer (MIT) as a self-hosted fallback. In an IISc benchmark (Aug 2026, averaged over datasets) its Telugu word error rate was 26.4% vs 28.7% for Saaras v3. - Avoid Whisper and faster-whisper for Telugu. - Bhashini's free APIs are for proof-of-concept only; commercial use needs a paid plan agreed with them. (2) OCR: Claude vision with structured outputs for invoices, serial labels and box photos, always checked by deterministic code (barcode decode, GTIN check digit). Claude never invents a SKU. - Avoid AWS Textract: it reads only EN/ES/DE/IT/FR/PT. - Google Document AI Enterprise OCR supports Telugu and Hindi; keep it as a fallback (about $1.50 per 1,000 pages). - PaddleOCR (Apache-2.0, now has an official JS SDK) is a later self-host option. (3) Barcodes on the web: use the native BarcodeDetector where it exists (Chrome Android 83+). Everywhere else, including US investors on iPhones, use the MIT barcode-detector / zxing-wasm polyfill with the .wasm file self-hosted. - Avoid html5-qrcode and @zxing/library: both are in maintenance mode. - Use expo-camera when the mobile app starts. (4) Embeddings: Voyage voyage-4-lite into pgvector. - $0.02 per 1M tokens, with 200M free tokens per model. Embedding 100,000 product titles of about 50 tokens each costs about $0.10. - multilingual-e5-small (MIT, 118M parameters, ONNX via transformers.js) is the offline fallback. - We have not verified Voyage quality on Telugu/Hindi titles; test it first. (5) Observability: Langfuse. The core is MIT; the ee/ folders have a separate licence. - Cloud regions are US, EU, Japan and HIPAA only. There is no India region, so either redact personal data or self-host in Mumbai. - Langfuse accepts OTLP over HTTP and maps gen_ai.* attributes. ## UI quality gates: accessibility, performance, i18n, testing

**Summary (from research):** I checked every tool on npm, GitHub or its official site on 2026-09-30. The web setup that works: WCAG 2.2 AA as the standard. For accessibility checks, axe-core via @axe-core/playwright and the Storybook 10 a11y addon, plus jsx-a11y lint. Playwright 1.63 covers E2E and screenshot testing, run inside the pinned Docker image. Performance uses Lighthouse 13 and Lighthouse CI for lab numbers, and PostHog for real-user Core Web Vitals and masked session replay. Bundles are checked with `next experimental-analyze`. The i18n stack is next-intl 4.14.8 with ICU messages and Intl formatting. Tolgee Cloud Free is the workspace for Telugu and Hindi reviewers. UX writing starts from the GOV.UK error-message rules, and usability is tested in person with 5 users per round. Avoid Lost Pixel (repo archived 2026-04-22), Microsoft Clarity on India buyer pages (Microsoft is the data controller), switching to Lingui, and Maze for first-time Telugu users. Six traps I confirmed: (1) axe's WCAG 2.2 target-size rule is off by default. It runs only if you add the `wcag22aa` tag, and Playwright's docs example leaves that tag out. (2) ESLint 9 reached end of life on 2026-08-06, but Next 16.3's scaffolder still installs `eslint ^9`. eslint-plugin-jsx-a11y (last release Oct 2024) does not list ESLint 10 in its peer range. (3) Next 16 dropped `size` and `First Load JS` from `next build` output, so you need a separate JS budget. (4) Lighthouse CI 0.15.1 still bundles Lighthouse 12.6.1. (5) `Intl` compact notation in `te` gives "1.2మి" (million), not lakh. (6) Hindi plural rules put 0 in the 'one' category, so every plural message needs an explicit `=0` case. INVESTOR-DEMO GATE.
